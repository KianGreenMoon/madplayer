A review of the swarm playback path as it stands after the eight 2026-08-15
commits (streaming, first-byte budget, relay resume, join-in-flight). Scope:
`internal/remote`, `internal/blobcache`, `internal/backend/swarm.go`,
`internal/mesh`, `internal/madshare/mesh.go`, and the player's streaming half —
plus the madshare side of every claim the client code makes about it.

One thing the review set out to check and can close positively: **the
reuse boundary held.** Nothing in this client re-derives a swarm rule — the
transfer engine, chunk verification, `WaitFor`/`Available` streaming surface
and holder discovery are all madshare's, reached through the facade, and where
the client needed something new it was added to madshare (`EnsureBlobFrom`,
the holders endpoint, token presentation) rather than reimplemented here.

Rules this file follows, inherited from madshare's `.issues/open-issues.md`:

- A finding is only closed when the **code** shows it closed.
- **Do not fix an issue that has not been reproduced.** Rows below say
  explicitly whether they were reproduced by a running test or confirmed by
  reading. Three rows carry a repro recipe that failed deterministically on
  this tree; re-create the test from the recipe before touching the fix.
- A fix that needs madshare is a madshare **design question**, not a client
  workaround — build the workaround if one exists, write down the real fix,
  and ask (this is row 1's situation).

| Severity | Issue | Status |
|---|---|---|
| **High** | **An abandoned swarm transfer runs to completion — and the client is built on the belief that it doesn't.** madshare's transfers run on the *node's lifetime context*, on purpose: `federation/transfer.go` (`EnsureBlob` doc, ~line 550) says "it outlives the requester on purpose (cache-through)", and `ensureBlob` launches `go n.runTransfer(t, holders)` detached, bounded only by `n.transferCtx`. That is the right shape for a server relaying to a browser. This client assumes the opposite in three places: (1) `backend/swarm.go` `FetchBlob`'s ctx.Done arm says "the transfer is governed by the same context, so abandoning it here is enough — it winds itself down" — **false**; (2) `blobcache`'s "a person skipping through ten tracks should not be downloading ten" holds only for the relay half — skipping cancels the blobcache copy, but the federation transfer underneath keeps pulling chunks to completion, and transfers for *different* hashes accumulate (`smu` serializes starting fetches, not orphaned transfers); (3) worst, the **first-byte decline path**: when `StreamBlob`'s `WaitFor` misses the budget, `fill` falls back to the relay while the swarm transfer keeps running — so every budget miss downloads the track **twice in parallel**, on exactly the link that was too slow to answer in 20s. Side effect: an orphaned cross-server transfer keeps requesting chunks after the next fetch installs a different server's token (`Enrolment.Present`), presenting the wrong vouch — holder 403s that pollute the per-holder stats rows `logTransfer` prints. The mitigation is real and should be weighed, not ignored: orphaned bytes land in madshare's cache, get seeded and advertised (`Holdings`), and make a re-click instant — that is the household working. But it is unbounded, unchosen, and documented as the opposite. **No client-side fix exists**: `federation.Transfer` exposes `Done/Err/Open/WaitFor/Available/Stats` and no cancel; `app.Network.Fetch` passes nothing that governs the run. The real fix is a madshare surface — a per-transfer abandon, or a caller-governed mode of `EnsureBlobFrom` for listener nodes (a player is not a cache-through relay; nobody else is waiting on its transfers). Until then the honest client move is to fix the three comments so the belief stops propagating. | **FIXED 2026-08-15 — the madshare surface was built** (owner authorized): `federation.Transfer` gained `Abandon()`, cancelling a per-transfer context derived from the node's (`federation-access.md` §household documents it; server code never calls it; `TestAbandonStopsARunningTransfer` pins that an abandoned mid-flight transfer ends promptly, errors, and leaves the active list). This client abandons at its three sites — `StreamBlob`'s declined first byte and failed `Open`, `swarmReader.Close` (a no-op after EOF, the stop on a skip), and `FetchBlob`'s expired wait — and all three wrong comments now state the true lifetime. Tests: `backend/abandon_test.go` (all three sites, against a stub transfer that counts `Abandon` calls). The wrong-token side effect dies with the orphans; the mitigation half (orphaned bytes seeding the household) is knowingly given up — a fetch nobody wants is the player's bandwidth, and seeding is served from completed fetches. |
| **Medium** | **A clicked track can wait out a prefetch's entire transfer before making any sound.** Reproduced (test below, failed 2.0s/2.0s deterministically). Mechanism, three parts that are each fine alone: (1) `fromSwarm` holds `smu` for the whole streamed transfer — when the budget bounded the *whole* fetch this was ≤20s, now it is the transfer's duration, minutes on a slow mesh; (2) `Prefetch` returns early when the wanted track is already cached (`fetch.go:369`) **before** the "cancel the running prefetch" step, so a running prefetch survives; (3) the clicked track's `fromSwarm` blocks on `smu.Lock()` *before* its budget starts, so neither the swarm attempt nor the relay fallback can begin. The player shows "loading" on a context with no deadline — indefinitely. Reachable when next-of-clicked is already cached, or equals the track being prefetched (replaying the previous track); ordinary clicks are saved by `prefetchNext` cancelling the old guess. The chain that usually keeps `smu` safe is worth writing down so it stops being re-derived: a playing track's fetch releases it because closing the reader drops the last blobcache waiter, which cancels the fetch ctx, which aborts the `io.Copy` — every step is load-bearing. **Repro:** in `internal/remote`, a `fakeSwarm` whose `stream` is a reader that blocks forever; `Prefetch` a track, wait for `sw.calls==1`, then `Local` a different track with a 2s ctx and `SetSwarmBudget(100ms)` — healthy behaviour is relay fallback in ~200ms, observed is `context deadline exceeded` at 2s. **Fix ideas:** bound the wait for `smu` by the budget too (a `TryLock` loop or acquiring inside the `hctx` deadline, declining to the relay on timeout — the smaller change), or make playback preempt the guess (cancel any running prefetch when `fill` runs for a different key — the tidier one, since a guess should never outrank a click). | **FIXED 2026-08-15 — all three parts, because each was a hole on its own.** (1) `smu` became `slot`, a one-place semaphore whose acquisition is bounded by the budget — a contender that cannot have the mesh in time declines to the relay, which closes the class for *every* contender (a keep-on-device holding the slot starves nobody either); (2) `fill` preempts a running prefetch for a different key (`preemptPrefetch`) — a guess never outranks a real fetch, so the common case still gets the swarm rather than the relay; (3) `Prefetch`'s cancel-the-stale-guess step now runs *before* the cached-early-return — "Prefetch(x)" means the guess changed, so whatever else was running is stale even when x is already on disk. The repro became `TestAClickedTrackIsNotStarvedByAPrefetchMidTransfer`; the other two parts are pinned by `TestARealFetchPreemptsARunningPrefetch` and `TestANewPrefetchStopsTheStaleOneEvenWhenCached` (`remote/priority_test.go`). |
| **Medium** | **Joining a fetch between the last reader leaving and the fetch's teardown attaches the new caller to a dead fetch — and the click silently does nothing.** Reproduced (3/3 runs). `blobcache.drop` decides `last := waiters == 0` under `mu` but cancels outside it, and `startFetch`'s goroutine removes the call from `inflight` only when the fetch body *returns* — real fetches take teardown time to notice cancellation (an HTTP body read has to fail first). Any `Stream`/`Get` for the same key in that window finds the call still in `inflight`, joins it (`waiters++`), and inherits `context.Canceled` when the dying fetch finishes. The player then treats that error as "the user skipped" (`player.load`: `errors.Is(err, context.Canceled)` → no error row, no advance) — so the visible symptom is a click that does nothing, with nothing logged. Trigger shape: skip away from a track and immediately click it again, or a prefetch being abandoned at the moment playback asks for the same track. **Repro:** copy `cache.go`+`stream.go` to a scratch module; fetch fn blocks on ctx then sleeps 150ms before returning `ctx.Err()`; `Stream`, close the reader, `Stream` the same key again with a fetch that writes bytes — the second read fails with `context canceled` every time. **Fix idea:** decide "last" and remove the call from `inflight` in the *same* critical section (the `call` needs to carry its key), so a caller arriving after the decision starts a fresh fetch; the dying goroutine's own `delete` stays as the normal path and is idempotent. | **FIXED 2026-08-15** exactly as scoped — `drop` decides "last" and unregisters in one critical section (the `call` carries its key), and the fetch goroutine's delete is guarded by identity so a dying call cannot evict its successor. **One consequence had to be paid for:** a fresh fetch starting during the old one's teardown must not share its part file (the dying fetch's handle points at the same inode, and one late write could land in — worst case — the renamed final file). Part names now carry a per-fetch sequence number (`<key><ext>.<seq>.part`), still `.part`-suffixed so the startup reaper and the entries walk treat them as before (`TestSequencedPartFilesAreReapedAtOpen`). Repro became `TestAJoinerAfterTheLastDropGetsAFreshFetch` (`blobcache/teardown_test.go`). |
| Low | **A failed fetch's `.part` file survives until the next launch when the last waiter leaves before the fetch has finished dying.** Reproduced. `drop`'s cleanup is a **non-blocking** `select` on `cl.done`: when the last reader closes while the fetch is still tearing down (the common case — the close is what *causes* the cancellation), `done` is not yet closed, the `default` arm runs, and nobody ever removes the part file; the fetch goroutine deliberately leaves it for `drop` to clean. Bounded harm: one orphan per abandoned fetch per session, swept by `reapPartials` at next start. Same window as the row above and the same fix neighbourhood — whoever restructures `drop` should have the *fetch goroutine* remove the part when it finishes with an error and `waiters` is already 0 (it knows both facts). | **FIXED 2026-08-15** with that exact shape: `cl.err` moved under `Cache.mu` so drop can ask "did it fail?" before `done` closes, and the two cleanup sites partition the race — drop removes when the fetch already failed, the fetch goroutine removes when it fails orphaned. Every interleaving lands in exactly one of them. Test: `TestAPartFileIsRemovedWhenTheFetchDiesAfterTheLastDrop`. |
| Low | **The holder lookup and the first byte each get a full budget; the comment says they share one.** `fetch.go` `fromSwarm`: the comment reads "The holder lookup shares the first-byte budget: it is part of 'the swarm answered'" — but `Holders` runs under its own `context.WithTimeout(ctx, f.budget())` and then `StreamBlob` is handed a fresh `f.budget()` as `firstByte`. Worst case is 2× budget (40s) of "loading" before the relay gets its turn: a server slow to answer holders eats one budget, a swarm slow to first byte eats another. Fix: compute one deadline up front and pass `time.Until(deadline)` as `firstByte` (floor it at zero → decline), which makes the code do what the comment already promises. | **FIXED 2026-08-15**, and the slot acquisition (row 2's fix) joined the same deadline — one budget covers slot + holder lookup + first byte, because they are one question ("did the swarm answer?"). Zero-or-less remaining is an ordinary decline. Test: `TestTheHolderLookupAndTheFirstByteShareOneBudget` (a 300ms holder delay must visibly shrink the first-byte allowance out of a 1s budget). |
| Info | **`backend.FetchBlob` has no caller, and its comment names one that uses a different path.** Its doc says it is "kept for the one job that genuinely wants every byte before it starts — keeping a track on this device", but `materialize.Keeper.Keep` calls `Fetcher.Local` (the swarm-then-relay fill into the blobcache), not `FetchBlob`. The trap worth recording: a future direct `FetchBlob` caller would bypass **both** the vouch (`Enrolment.Present` — no token presented, so a third-party holder 404s the fetch) and the one-fetch-at-a-time rule (`smu`) — both live in `remote.Fetcher`, not in the backend. Either wire keep-on-device through it deliberately (with those two rules moved or duplicated on purpose) or fix the comment to say what it is now: the facade's blocking fetch, currently unused, dangerous to call without a fetcher in front. Its ctx.Done comment also carries row 1's wrong governance claim. | **FIXED 2026-08-15** — the comment now states what it is (no caller; keep-on-device goes through `Fetcher.Local`) and names the trap for a future direct caller (no vouch, no slot — both live in the fetcher). Kept rather than deleted: it is the facade's blocking fetch and its ctx arm is one of the three `Abandon` sites, pinned by `TestFetchBlobAbandonsOnACancelledWait`. |
| Info | **Signing out of a server leaves its token installed as the presented vouch.** `Enrolment.SetServers` calls `RemoveHome` for a dropped server but never clears `node.SetToken(...)` when `presented` was that server's base. Inert in practice: every mesh fetch calls `Present` for its own server first, and the stale token simply expires within the hour; there is no request path that would present it meaningfully in between. Recorded so it is not rediscovered as a security finding — the token's worth was always bounded by the bearer key check on the far side, not by the client forgetting it. | **FIXED 2026-08-15**: `SetServers` clears `presented` and calls `node.SetToken("")` when the dropped server was the presented one — and only then, so a fetch's installed vouch survives signing out of some *other* server. Test: `TestSigningOutOfThePresentedServerClearsTheToken`. |

## What was checked and held up

Recorded so the next review does not re-tread it:

- **Resume-over-relay is sound end to end.** The resume offset is the meter's
  count of bytes actually written to the part file; `OpenFrom` refuses a 200
  answer to a range request rather than appending a second prefix; the two
  facts the splice rests on (per-chunk verification before readability,
  content-addressed identity) are both real on the madshare side.
- **The vouch/fetch interlock is right.** Token installed inside `smu`, fetch
  indivisible from presentation, and `enrol` re-presents a renewed token only
  when its server's token is the one on the wire.
- **Waiter accounting closes.** Every `begin` has a matching `drop` on all
  paths read (player skip, decode failure, prefetch abandonment, `Get`
  cancellation) — the leak-shaped bugs are the two race rows above, not a
  missing drop.
- **The decoders' seekability trick is guarded where it must be.**
  `player.Seekable` stands between a scrub and beep-mp3's documented panic on
  a non-seeking source; streamed sources answer `false` by construction.
- **`serverFor`'s longest-prefix match** handles the reverse-proxy-subpath
  deployment; hash-keyed cache names dedupe the same audio across servers.
- The full test suite is green on this tree as reviewed
  (`go test ./...`, 2026-08-15).
